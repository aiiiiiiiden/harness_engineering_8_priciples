## 이 장에서 배우는 것

이 장을 끝내면 **왜 하필 "12-Factor"라는 틀을 빌려왔는지**, 그리고 2011년의 웹앱 방법론에서 무엇이 에이전트로 넘어오고 무엇이 새로 쓰여야 했는지 설명할 수 있습니다. 1장에서 "하네스가 8할"이라고 했다면, 이 장은 *"그 8할을 어떤 항목으로 쪼개야 빠짐없이 단단해지는가"* — 즉 12개라는 목록 자체의 정당성을 다룹니다.

## 핵심 개념

**12-Factor Agents는 "프로덕션에서 죽지 않는 에이전트"가 갖춰야 할 12가지 설계 원칙의 목록이다.** 이 목록은 [Heroku의 12-Factor App](https://12factor.net) — Adam Wiggins, 2011 — 에서 **이름과 형식을 빌려왔습니다**. 12-Factor App은 "클라우드에서 죽지 않는 웹앱"의 조건 12가지를 정리한 방법론이고, 그 영향력 덕에 "12개의 명시적 원칙으로 신뢰성을 정의한다"는 형식이 하나의 장르가 되었습니다.

여기서 가장 중요한 사실 하나. **둘은 이름과 형식을 공유할 뿐, 서로 다른 대상을 다루는 별개의 문서입니다.** 12-Factor App의 항목(Codebase, Config, Processes…)을 그대로 에이전트에 1:1로 대응시킬 수는 없습니다. 12-Factor Agents는 HumanLayer(Dexter Horthy 주도)가 **에이전트라는 새 대상에 맞춰 12개 항목을 새로 쓴** 목록입니다. 빌려온 것은 항목이 아니라 *태도*입니다.

그 태도를 한 줄로 줄이면 이렇습니다:

> 신뢰성은 마법이 아니라 **명시적으로 소유한 계약(contract)의 합**이다. 암묵적으로 프레임워크에 맡긴 것은 프로덕션에서 깨진다.

12-Factor App이 설정·상태·로그를 "환경에 숨기지 말고 명시적으로 다뤄라"라고 했듯, 12-Factor Agents는 프롬프트·컨텍스트·제어 흐름·상태를 "프레임워크에 숨기지 말고 직접 소유하라"라고 말합니다. 1장의 언어로는, 하네스를 남에게 위임하지 말라는 뜻입니다.

## 왜 중요한가

"굳이 12개씩이나 외워야 하나, 그냥 잘 만들면 되지"라는 반문이 자연스럽습니다. 목록이 필요한 이유는 **빠뜨림을 막기 위해서**입니다.

에이전트가 프로덕션에서 무너지는 방식은 1장에서 봤듯 제각각입니다 — 컨텍스트 오염, 에러 누적, 상태 유실, 재현 불가. 이걸 "에이전트를 잘 만들자"는 한 덩어리 목표로 두면, 사람마다 떠올리는 체크 항목이 다르고 반드시 어딘가 구멍이 납니다. 12-Factor App이 등장하기 전 웹 배포가 그랬습니다. "서버에 잘 올리자"는 말로는, 설정을 코드에 하드코딩한 사람과 로컬 디스크에 세션을 저장한 사람을 막을 수 없었습니다. **명시적 목록은 "무엇을 점검했는지"를 셀 수 있게 만듭니다.**

App에서 Agent로 넘어오며 무게중심이 어떻게 옮겨갔는지 보면, 왜 항목을 새로 써야 했는지가 분명해집니다.

| 축 | 12-Factor App (웹 프로세스) | 12-Factor Agents (LLM 에이전트) |
|---|---|---|
| 무엇이 무상태여야 하나 | 웹 프로세스 (Factor 6 Processes) | 에이전트 루프 — 상태는 밖에, 에이전트는 reducer (Factor 12) |
| 핵심 입력 계약 | 설정을 환경변수로 (Config) | 자연어를 도구 호출로 (Factor 1·4) |
| 무엇을 직접 소유하나 | 의존성·빌드를 명시 (Dependencies) | 프롬프트·컨텍스트·제어 흐름 (Factor 2·3·8) |
| 죽었다 살아나는 법 | 빠른 시작·우아한 종료 (Disposability) | 간단한 API로 시작·중단·재개 (Factor 6) |
| 관측 가능성 | 로그를 이벤트 스트림으로 (Logs) | 에러를 컨텍스트에 압축 (Factor 9) |

> 이 표는 **개념적 유사성**을 보여줄 뿐, 정본의 1:1 매핑이 아닙니다. 12-Factor App의 "Factor 6 Processes"와 12-Factor Agents의 "Factor 6 시작·중단·재개"는 번호가 같아도 다른 항목입니다. 두 문서의 factor 번호를 섞어 인용하면 안 됩니다.

웹앱에서는 프로세스 하나가 요청을 받아 응답하면 끝이라, "무상태"가 비교적 쉬웠습니다. 에이전트는 다릅니다. 여러 턴에 걸쳐 도구를 부르고, 사람을 기다리고, 중간에 끊겼다 재개됩니다. 그래서 "상태를 어디에 둘 것인가", "끊긴 자리를 어떻게 복원할 것인가"가 훨씬 무겁고, App 시절엔 없던 **컨텍스트 윈도**라는 자원을 새로 관리해야 합니다. 항목을 새로 쓸 수밖에 없었던 이유입니다.

## 하네스에 적용하기

원칙이 있고 없고의 차이는 코드에서 가장 선명합니다. "그냥 잘 만든" 데모 봇은 보통 이렇게 생겼습니다.

```python
# 안티: 설정·상태·제어 흐름이 전부 암묵적. 어느 factor도 명시적으로 소유하지 않았다.
def deploy_bot(pr_url):
    while True:
        msg = llm.chat(f"PR {pr_url} 처리해줘. 다음에 뭐 할까?")   # 프롬프트가 코드에 묻힘
        if "deploy" in msg:                                       # 자연어를 문자열로 파싱
            os.system("deploy.sh")                                # 결과 검증 없음
        # 상태는 어디에도 저장되지 않는다 → 끊기면 처음부터
```

같은 봇을 "각 factor를 누가 책임지는지" 명시하도록 다시 쓰면, 1장에서 본 루프가 됩니다 — 차이는 **각 줄의 책임이 목록의 한 항목에 대응한다는 점**입니다.

```python
# 12-Factor: 각 책임이 명시적이고, 상태는 밖에 있어 재개 가능하다.
def deploy_bot(state):                      # 상태를 인자로 받는다 = 무상태 reducer (Factor 12)
    ctx = build_context(state)              # 컨텍스트를 직접 구성     (Factor 3)
    step = llm.decide(ctx)                  # 자연어를 도구 호출로 변환     (Factor 1)
    result = run_tool(step)                 # 하네스가 구조화된 도구 호출을 검증·실행 (Factor 4)
    return reduce(state, step, result)      # 새 상태를 반환 → 저장·재개 (Factor 5·6)
```

이 책의 집필 하네스도 같은 원리를 따릅니다. "책을 잘 쓰자"를 한 덩어리로 두지 않고, 구조는 `docs/toc.json`이, 사실은 `docs/verified-facts.md`가, 검증은 `scripts/verify.py`가 **항목별로 명시적으로** 소유합니다. 어느 하나가 비면 `verify.py`가 셀 수 있게 잡아냅니다 — 12개 목록이 빠뜨림을 막는 것과 같은 메커니즘입니다.

## 안티패턴과 함정

- **App의 factor를 Agent에 그대로 이식하기:** "12-Factor App에 Config가 있으니 에이전트도 환경변수만 잘 쓰면 된다"는 식. 두 문서는 다른 대상을 다룹니다. App의 목록을 외워 에이전트에 적용하면 컨텍스트·제어 흐름처럼 에이전트 고유의 항목을 통째로 놓칩니다.
- **출처를 헷갈리기:** 12-Factor Agents를 "Heroku가 만든" 또는 "OpenAI/Anthropic이 만든" 것으로 적는 것. 정본은 **HumanLayer(Dexter Horthy)** 가 정리했고, 12-Factor **App**(Heroku, Adam Wiggins, 2011)에서 영감만 받았습니다.
- **"13번째 factor"를 정본처럼 인용:** 일부 글이 pre-fetch context 등을 13번째로 덧붙이지만, **정본은 12개**입니다. 추가 항목을 인용할 땐 "비정본"임을 명시하세요.
- **목록을 체크박스로만 소비하기:** 12개를 "다 했음"으로 도장 찍고 끝내는 것. 목록의 목적은 점검을 *셀 수 있게* 만드는 것이지, 통과 도장 자체가 신뢰성을 보장하진 않습니다.

## 핵심 정리 / 체크리스트

- [ ] 12-Factor Agents는 **HumanLayer**가 정리했고, 12-Factor **App**(Heroku, Adam Wiggins, 2011)에서 **이름·형식만** 빌렸다 — 다루는 대상은 다르다.
- [ ] 빌려온 것은 항목이 아니라 *태도*다: **신뢰성 = 명시적으로 소유한 계약의 합.**
- [ ] 목록이 필요한 이유는 **빠뜨림을 막고, 무엇을 점검했는지 셀 수 있게** 하기 위해서다.
- [ ] App→Agent로 오며 무상태의 대상이 웹 프로세스에서 **에이전트 루프**로 옮겨갔고, **컨텍스트 윈도**라는 새 자원이 생겼다.
- [ ] 두 문서의 factor **번호를 섞어 인용하지 않는다**. 정본은 **12개**이며, 추가 factor는 비정본으로 명시한다.
