## 이 장에서 배우는 것

이 장을 끝내면 **"하네스(harness)"가 무엇이고 왜 LLM 에이전트의 신뢰성을 좌우하는지** 설명할 수 있습니다. 그리고 이 책 전체를 관통할 질문 하나를 손에 쥐게 됩니다 — *"내 에이전트에서 LLM이 책임지는 부분은 어디까지이고, 나머지는 누가 책임지는가?"*

## 핵심 개념

**하네스란, LLM 호출을 감싸서 그것을 '제품'으로 만드는 결정론적 코드 전체다.** 도구 실행, 제어 흐름(루프·분기), 컨텍스트 구성, 상태 저장, 검증·재시도 — 모델이 토큰을 뱉는 그 한 번의 호출을 제외한 거의 모든 것이 하네스입니다.

`harness`는 원래 말에게 씌우는 **마구(馬具)** 입니다. 말의 힘 자체를 만들어내지는 않지만, 그 힘이 엉뚱한 데로 새지 않고 수레를 끄는 방향으로 향하게 잡아줍니다. LLM이 말이라면, 하네스는 그 힘을 제품이 원하는 방향으로 채널링하는 마구입니다. 소프트웨어 테스트의 "test harness"(테스트 대상을 실행·관찰 가능하게 감싸는 장치)와도 같은 결입니다.

12-Factor Agents의 저자 HumanLayer(Dexter Horthy 주도)가 던지는 핵심 관찰은 이렇습니다:

> "우리가 본 'production-grade 에이전트' 대부분은 사실 그렇게 에이전트답지 않았다. 대부분은 잘 짜인 **결정론적 코드**였고, LLM은 그 사이사이 **전략적인 지점에만** 끼워져 있었다."

즉 좋은 에이전트일수록 "LLM에게 다 맡긴 마법"이 아니라, **하네스가 80%, LLM이 20%** 에 가깝습니다. 이 책이 다루는 12가지 원칙(12-Factor Agents)은 바로 그 80%, 하네스를 어떻게 설계해야 신뢰할 수 있는가에 대한 답입니다.

## 왜 중요한가

LLM 데모는 거의 항상 됩니다. 프롬프트 하나에 도구 몇 개를 붙이고 `while` 루프를 돌리면, 첫 시연에서는 마법처럼 동작합니다. 문제는 그 다음입니다.

같은 코드를 실제 사용자에게 내보내면 이런 일이 벌어집니다:

- 7번째 턴쯤 컨텍스트가 쓰레기로 가득 차 모델이 엉뚱한 도구를 부른다.
- 도구가 던진 스택트레이스가 그대로 컨텍스트에 쌓여 다음 판단을 오염시킨다.
- 세션이 끊기면 어디까지 했는지 아무도 모른다 — 처음부터 다시.
- 같은 입력인데 어제와 오늘 결과가 다르고, 왜 그런지 재현할 수 없다.

이건 모델이 약해서가 아닙니다. **하네스가 없어서** 입니다. 데모와 프로덕션을 가르는 것은 모델의 지능이 아니라, 그 지능을 둘러싼 결정론적 구조물의 견고함입니다. "프레임워크가 알아서 해주겠지" 하고 제어 흐름·컨텍스트·상태·검증을 남에게 위임한 만큼, 정확히 그만큼 프로덕션에서 무너집니다.

12-Factor Agents가 [Heroku의 12-Factor App](https://12factor.net) — Adam Wiggins, 2011 — 에서 이름을 빌려온 이유가 여기 있습니다. 12-Factor App이 "클라우드에서 죽지 않는 웹앱"의 조건을 정리했듯, 12-Factor Agents는 "프로덕션에서 죽지 않는 에이전트"의 조건을 정리합니다. (둘은 **이름만 닮은 다른 문서**입니다 — App은 배포 가능한 웹 서비스, Agents는 LLM 에이전트를 다룹니다.)

## 하네스에 적용하기

가장 단순한 에이전트 루프를 의사코드로 보면, 하네스가 어디에 있는지 한눈에 보입니다.

```python
# LLM이 책임지는 부분은 단 한 줄(next_step). 나머지가 전부 하네스다.
def run_agent(goal):
    context = build_context(goal)          # 하네스: 컨텍스트 구성   (Factor 3)
    while True:
        step = llm.decide(context)         # ← LLM (전체의 20%)      (Factor 1·4)
        if step.kind == "done":
            return step.result
        try:
            result = tools[step.name](**step.args)   # 하네스: 도구 실행 (Factor 4)
        except Exception as e:
            result = compact_error(e)       # 하네스: 에러를 짧게 압축 (Factor 9)
        context = append(context, step, result)      # 하네스: 상태 갱신 (Factor 5)
        if needs_human(step):
            return ask_human(step)          # 하네스: 사람에게 위임   (Factor 7)
```

`llm.decide` 한 줄을 뺀 나머지 — 컨텍스트를 어떻게 짤지, 도구를 어떻게 실행·검증할지, 에러를 어떻게 압축할지, 상태를 어디에 둘지, 언제 사람을 부를지 — 이 전부가 하네스고, 12가지 원칙이 다루는 영역입니다. 주석에 달린 Factor 번호처럼, 이 책의 2부는 이 루프의 각 줄을 한 장씩 분해합니다.

**이 레포가 곧 살아있는 예시입니다.** 지금 읽고 있는 이 책 자체가 하나의 하네스로 집필됩니다 — 구조는 `docs/toc.json`이, 사실은 `docs/verified-facts.md`가, 검증은 `scripts/verify.py`와 codex 교차검증이 책임지고, LLM(저자 Claude)은 "문장을 쓰는" 전략적 지점에만 들어갑니다. 4부에서 이 하네스를 직접 해부하고 12가지 원칙으로 채점합니다.

> **이 책의 러닝 예제 — "배포 봇".** 앞으로 하나의 가상 에이전트를 함께 단단하게 만들어 갑니다. PR을 받아 테스트를 돌리고 스테이징에 배포하는 "배포 봇"입니다. 1부의 배포 봇은 데모 수준이고, 12개 장을 지나며 한 factor씩 적용해 프로덕션에서 죽지 않는 봇으로 키웁니다.

## 안티패턴과 함정

- **"프레임워크가 다 해준다"** — 추상화 한 겹 뒤에 제어 흐름·컨텍스트·프롬프트를 숨기면, 문제가 터졌을 때 들여다볼 수가 없습니다. 하네스는 *내가 소유해야* 하는 코드지, 위임 대상이 아닙니다(Factor 2·8).
- **에이전트를 의인화하기** — "에이전트가 알아서 판단하겠지"라며 결정론으로 처리할 수 있는 일까지 LLM에 떠넘기는 것. 분기 하나로 끝날 일을 매번 모델에 묻지 마세요.
- **하네스를 0%로 두기** — 프롬프트 + `while` 루프만으로 프로덕션에 나가는 것. 데모는 통과하지만 위에서 본 네 가지 방식으로 무너집니다.
- **하네스를 100%로 두기** — 반대로 모든 걸 하드코딩해 LLM의 유연함을 죽이는 것. 핵심은 "LLM이 잘하는 일(모호한 자연어 해석)"과 "코드가 잘하는 일(결정론·검증·상태)"의 **경계를 의도적으로 긋는 것**입니다.

## 핵심 정리 / 체크리스트

- [ ] 하네스 = LLM 호출 한 번을 제외한, 에이전트를 제품으로 만드는 **결정론적 코드 전체**.
- [ ] 데모→프로덕션 격차는 모델 지능이 아니라 **하네스의 견고함**이 만든다.
- [ ] 좋은 에이전트는 "하네스 多 + LLM 少". 12가지 원칙은 그 하네스의 설계 지침이다.
- [ ] 모든 설계 결정 앞에서 물어라: *"이건 LLM이 책임질 일인가, 하네스가 책임질 일인가?"*
- [ ] 12-Factor Agents는 HumanLayer가 정리했고, 12-Factor App(Heroku)에서 **이름만** 빌렸다.
