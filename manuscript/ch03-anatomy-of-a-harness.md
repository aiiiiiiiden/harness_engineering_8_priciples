## 이 장에서 배우는 것

이 장을 끝내면 **하네스를 다섯 개의 부품으로 분해해서 볼 수 있고**, 12개 원칙이 각각 그중 어느 부품에 사는지 지도를 손에 쥐게 됩니다. 동시에 이 책을 따라오며 손으로 만질 **실습 환경**(Claude Agent SDK·MCP·구조화 출력·codex)을 미리 둘러봅니다. 1·2장이 "왜 하네스인가"였다면, 이 장은 "그 하네스가 실제로 어떤 부품으로 되어 있나"입니다.

## 핵심 개념

1장에서 하네스를 "LLM 호출 한 번을 뺀 결정론적 코드 전체"라고 뭉뚱그렸습니다. 이제 그 덩어리를 **다섯 개의 부품**으로 해부합니다. 어떤 에이전트든 결국 이 다섯이 돌고 있습니다.

| 부품 | 책임 | 주로 사는 factor |
|---|---|---|
| **컨텍스트 빌더** | 모델에게 무엇을 보여줄지 구성 | 2·3 (프롬프트·컨텍스트 소유) |
| **모델 호출부** | 자연어를 구조화된 결정으로 변환 | 1·4 (도구 호출·구조화 출력) |
| **도구 실행부** | 결정을 실제 부수효과로 실행·검증 | 4·7 (도구·사람 호출) |
| **제어 루프** | 다음에 무엇을 할지, 언제 멈출지 | 8·10 (제어 흐름·작은 에이전트) |
| **상태 저장소** | 어디까지 했는지 기록·복원 | 5·6·12 (상태 통합·재개·reducer) |

비유하자면 자동차 엔진의 분해도와 같습니다. "차가 달린다"는 한 문장 안에는 실린더·점화·연료·변속·냉각이 따로 돌고 있고, 고장은 항상 *특정 부품*에서 납니다. 하네스도 마찬가지여서, "에이전트가 이상해요"는 진단이 아니라 **"어느 부품이 깨졌나"** 로 좁혀야 고칠 수 있습니다. 12개 원칙은 이 다섯 부품을 빠짐없이 점검하기 위한 좌표입니다.

남은 factor 9(에러 압축)와 11(어디서든 트리거)은 특정 부품이 아니라 **부품 사이를 흐르는 신호**에 가깝습니다. 에러가 상태 저장소로 어떻게 들어가는가, 트리거가 제어 루프를 어디서 깨우는가. 2부에서 한 장씩 짚습니다.

## 왜 중요한가

부품으로 보지 않으면, 디버깅이 점(占)이 됩니다.

"7번째 턴에서 봇이 엉뚱한 도구를 불렀다"는 증상을 만났다고 합시다. 하네스를 한 덩어리로 보는 사람은 프롬프트를 이리저리 바꿔보며 운에 맡깁니다. 부품으로 보는 사람은 다르게 묻습니다 — *컨텍스트 빌더가 쓰레기를 넣었나(Factor 3), 모델 호출부의 출력이 구조화돼 있지 않았나(Factor 4), 아니면 상태 저장소가 이전 턴을 잘못 복원했나(Factor 5)?* 증상 하나를 부품별 질문으로 쪼개는 순간, 고칠 수 있는 문제가 됩니다.

이게 이 책이 **장 = factor = 부품의 한 단면**으로 구성된 이유입니다. 2부의 각 장은 추상적인 격언이 아니라, 이 분해도의 한 부품에서 무엇이 어떻게 깨지고 어떻게 막는지를 다룹니다.

## 하네스에 적용하기

다섯 부품은 추상이 아니라 코드의 자리입니다. 1장의 배포 봇 루프에 부품 이름을 달면 이렇게 보입니다.

```python
def run_agent(state):
    ctx   = build_context(state)        # [컨텍스트 빌더]
    step  = llm.decide(ctx)             # [모델 호출부]  ← 여기만 LLM
    result = run_tool(step)             # [도구 실행부]
    state = reduce(state, step, result) # [상태 저장소]
    return state                        # 한 턴을 끝내고 새 상태를 반환
```

이 함수는 **한 턴**만 돌고 끝납니다. `while`이 안 보이는 건 의도된 것입니다. **[제어 루프]는 이 함수 밖**에서 이 함수를 언제 다시 부르고 언제 멈출지 결정합니다(Factor 8·12의 핵심이며, 11·15장에서 깊이 다룹니다). 부품을 함수 안에 다 욱여넣지 않는 것 자체가 무상태 설계의 출발점입니다.

이 책의 **실습 환경**은 이 다섯 부품을 실제로 만져볼 수 있는 도구로 구성됩니다. 모두 공개 도구라 독자가 그대로 따라 할 수 있습니다.

- **Claude Agent SDK** — 모델 호출부와 제어 루프에 닿는 부품을 다루는 실습 도구. (과거 "Claude Code SDK"에서 이름이 바뀌었습니다.) 에이전트 루프 실행, 도구 연동(커스텀 도구·MCP 서버), 세션 저장, 권한 제어 같은 골격을 제공해서, 바닥부터 짜는 대신 그 위에서 각 부품을 소유하는 법을 배웁니다. 공식 문서는 [code.claude.com/docs](https://code.claude.com/docs).
- **MCP(Model Context Protocol)** — 도구 실행부의 표준 인터페이스. 외부 도구를 에이전트에 꽂는 방식을 표준화합니다(명세: modelcontextprotocol.io).
- **구조화 출력(structured outputs)** — 모델 호출부와 도구 실행부의 계약. 모델의 결정을 자유 텍스트가 아니라 검증 가능한 스키마로 받습니다(Factor 4의 실물, 7장에서 깊이 다룹니다).
- **codex 같은 독립 모델 CLI** — 검증 부품. 한 모델이 쓴 것을 *다른 모델*이 교차검증하는 모델 다양성을 실습합니다. 단 독립성은 공짜가 아니라 설정의 결과입니다 — 집필에 쓴 것과 **다른 모델·벤더**로 codex를 띄워야 비로소 교차검증이 됩니다(3부 신뢰성 패턴의 핵심).

> **자기참조 — 지금 이 책이 그 실습 환경 위에 있습니다.** 이 원고는 위 도구들로 만든 하나의 하네스로 집필됩니다. 컨텍스트는 규약 문서가, 도구 실행은 검증·렌더 스크립트가, 교차검증은 codex가 맡습니다. 다만 이 레포만의 사적인 부품(자체 스크립트·커맨드)은 본문에서 *보조 예시*로만 비추고, 그 전체 해부도는 **4부 케이스 스터디**에서 부품 하나하나 열어 12개 원칙으로 채점합니다.

## 안티패턴과 함정

- **부품 경계를 뭉개기:** 컨텍스트 빌더가 도구를 직접 실행하고, 도구 실행부가 프롬프트를 만드는 식으로 책임이 섞이면, 한 곳을 고칠 때 다른 곳이 깨집니다. 부품의 가치는 *경계*에 있습니다.
- **실습 도구를 마법 상자로 쓰기:** Claude Agent SDK·MCP를 "알아서 다 해주는 프레임워크"로 받아들이면 1장의 "프레임워크가 다 해준다" 함정으로 되돌아갑니다. 이 책은 도구를 *쓰면서도 각 부품을 소유*하는 법을 가르칩니다.
- **검증 부품을 생략하기:** "같은 모델에게 한 번 더 물으면 검증"이라고 착각하는 것. 같은 모델은 같은 실수를 합니다. 교차검증의 핵심은 **다른 모델**(codex)이라는 독립성입니다.
- **명칭·출처를 흐리기:** "Claude Code SDK"(구 명칭)나 `docs.` 접두의 옛 주소로 적는 것. 현재 명칭은 **Claude Agent SDK**, 문서 도메인은 **code.claude.com/docs** 입니다.

## 핵심 정리 / 체크리스트

- [ ] 하네스는 다섯 부품으로 분해된다: **컨텍스트 빌더 · 모델 호출부 · 도구 실행부 · 제어 루프 · 상태 저장소.**
- [ ] 12개 원칙은 이 부품들에 흩어져 산다(예: 3→컨텍스트 빌더, 4→도구 실행부와 모델 호출부의 *계약*, 12→상태 저장소). factor 9·11은 부품 사이를 흐르는 신호다.
- [ ] "에이전트가 이상하다"가 아니라 **"어느 부품이 깨졌나"** 로 디버깅한다.
- [ ] 실습 환경 = **Claude Agent SDK · MCP · 구조화 출력 · codex**. 전부 공개 도구라 따라 할 수 있다.
- [ ] 명칭은 **Claude Agent SDK**(구 Claude Code SDK), 문서 도메인은 **code.claude.com/docs**.
