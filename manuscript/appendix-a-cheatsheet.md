## 이 장에서 배우는 것

이 부록을 책상 옆에 두면, 2부에서 한 장씩 풀어낸 **하네스 엔지니어링 8원칙**을 한 화면에서 떠올릴 수 있습니다. 각 원칙의 한 줄 정의, 핵심 강제 장치, 어겼을 때 무너지는 지점, 해당 장을 한 표로 모았습니다. 새 프로젝트를 시작하거나 에이전트가 헤맬 때, 어느 원칙이 빠졌는지 빠르게 짚는 점검표로 활용할 수 있습니다.

## 핵심 개념

먼저 전제부터 정직하게 밝혀두겠습니다. **원문(OpenAI, _Harness Engineering_, Ryan Lopopolo, 2026)은 원칙을 번호로 세지 않습니다.** 원문 본문은 11개 절로 이뤄지는데, 이 책의 8원칙은 그중 원칙을 담은 8개 절에서 한 원칙씩 선별·도출한 이 책의 커리큘럼입니다(나머지 3개 절 — 실험 도입부, "What \"agent-generated\" actually means", 맺음 — 은 맥락으로만 씁니다). 그래서 "원문이 정한 8원칙"이 아니라 **"원문에서 도출한 8원칙"** 입니다.

한 줄 명제는 전부 이 문장에서 갈라져 나옵니다.

> **사람이 조종하고, 에이전트가 실행한다(Humans steer, agents execute).**
> — OpenAI, _Harness Engineering_

| # | 원칙 (한국어 / 영문) | 한 줄 정의 | 원문 절 |
|---|---|---|---|
| 1 | **사람이 조종하고, 에이전트가 실행한다**<br>Humans steer, agents execute | 사람의 일은 코드 타이핑이 아니라 **환경 설계·의도 명시·피드백 루프 구축**으로 옮겨간다. | Redefining the role of the engineer |
| 2 | **애플리케이션을 에이전트가 읽게 하라**<br>Make the application legible to agents | 로그·상태·동작을 에이전트가 *관측*할 수 있게 앱을 계측한다. 눈이 없으면 "고쳤다"를 검증할 수 없다. | Increasing application legibility |
| 3 | **리포지터리 지식을 기록 시스템으로**<br>Repository knowledge as a system of record | 지식을 버전 관리되는 프로젝트 저장소 아티팩트로 둔다. 단 백과사전이 아니라 **지도**(짧은 `AGENTS.md`) + 구조화된 `docs/`. | We made repository knowledge the system of record |
| 4 | **에이전트 가독성에 최적화하라**<br>Optimize for agent legibility | 사람의 멋부린 취향보다 **에이전트가 읽기 쉬운 구조**(작은 진입점·명시적 경계·일관된 패턴)를 우선한다. | Agent legibility is the goal |
| 5 | **아키텍처와 취향을 기계적으로 강제하라**<br>Enforce architecture and taste mechanically | 규칙을 문서가 아니라 **린터·구조적 테스트·CI**로 강제한다. 강제되지 않은 규칙은 드리프트한다. | Enforcing architecture and taste |
| 6 | **처리량에 맞춰 병합 철학을 바꿔라**<br>Let throughput reshape merge philosophy | 에이전트 PR이 폭증하면 사람의 리뷰가 병목이 되어 버티지 못한다. **작은 PR·자동 검증·반복 루프**로 병합 정책을 재설계한다. | Throughput changes the merge philosophy |
| 7 | **자율 루프를 시스템에 인코딩하라**<br>Encode the autonomy loop | 반복 작업을 매번 사람이 트리거하지 말고 **백그라운드 태스크·루프**로 인코딩해 자율 수준을 점증시킨다. | Increasing levels of autonomy |
| 8 | **엔트로피를 가비지 컬렉션하라**<br>Garbage-collect entropy | AI 생성물의 드리프트(명명 표류·죽은 코드·문서 불일치)를 **"황금 원칙" + 반복 정리 태스크**로 GC한다. | Entropy and garbage collection |

> 원칙 번호·이름·순서의 마스터는 `docs/verified-facts.md` §2입니다. 원문 절 순서를 따르되, 원칙 6→7 사이에는 매핑하지 않은 개념 절("What \"agent-generated\" actually means")이 끼어 있어 **절과 원칙이 1:1로 맞물리지는 않습니다.**

## 왜 중요한가

치트시트의 진짜 쓸모는 **진단**입니다. 에이전트가 프로덕션 규모에서 무너질 때, 거의 항상 원칙 하나가 빠져 있습니다. 아래는 "이 원칙을 어기면 무엇이 터지는가"를 한 줄로 모은 진단표입니다. 데모에서는 안 보이다가 규모·시간에서 드러나는 증상들입니다.

| # | 원칙을 어기면 | 데모→프로덕션에서 터지는 지점 |
|---|---|---|
| 1 | 실패를 프롬프트로 때운다 | 같은 실수가 매 실행 반복. 수정이 한 번의 호출에만 적용되고 확장되지 않는다. |
| 2 | 로그·상태를 에이전트에 안 보여준다 | 에이전트가 "고쳤다"고 주장하지만 실제 동작은 아무도 모른다. 회귀가 조용히 쌓인다. |
| 3 | 결정을 채팅·머릿속에 둔다 | 에이전트에겐 없는 지식. 매번 다른 가정 위에서 코드를 짠다. |
| 4 | 사람 취향대로 영리하게 추상화한다 | 에이전트가 진입점에서 길을 잃고 로컬 패턴 매칭에 빠진다. |
| 5 | 규칙을 문서에만 적는다 | 장시간 자율 실행 동안 구조가 조용히 드리프트한다. 점검할 손잡이가 없다. |
| 6 | 사람의 병합 리뷰를 그대로 둔다 | 리뷰가 PR 생성 속도를 못 따라가 병목이 된다. 변경이 큐에 쌓인다. |
| 7 | 매번 사람이 작업을 트리거한다 | 자율이 사람의 주의력에 묶여 확장되지 않는다. 야간·주말에 멈춘다. |
| 8 | 엔트로피를 수동으로 청소한다 | 원문 사례: 금요일 수동 정리가 엔지니어링 시간의 **약 20%**를 먹고도 생성 속도를 못 따라갔다. |

## 하네스에 적용하기

각 원칙은 추상적 다짐이 아니라 **프로젝트 저장소 안의 구체적 부품**입니다. 아래는 원칙 → 핵심 강제 장치 → 샘플 프로젝트(`todo-api`)에서의 실물을 한 줄로 잇고, 책의 어느 장에서 다뤘는지를 가리키는 점프 표입니다.

| # | 핵심 강제 장치 | `todo-api`에서의 실물 | 해당 장 |
|---|---|---|---|
| 1 | 수용 가능한 기준 · 사람 리뷰 게이트 | `docs/exec-plans/active/*.md`(계획 + 의사결정 로그) | 2부 1장(ch04) |
| 2 | 구조화 로그 · 관측성 | 표준화된 로그 포맷, 메트릭 엔드포인트, LogQL/PromQL로 조회 가능한 관측성 | 2부 2장(ch05) |
| 3 | 맵 + 기록 시스템 | `AGENTS.md`(약 100줄) → `docs/`(design-docs·exec-plans·references) | 2부 3장(ch06) |
| 4 | 작은 진입점 · 명시적 경계 | 계층 모델(Types→Config→Repo→Service→Runtime→UI), 일관된 모듈 패턴 | 2부 4장(ch07) |
| 5 | 린터 · 구조적 테스트 · CI | 맞춤형 린터 + 구조적 테스트가 위반을 빌드에서 차단 | 2부 5장(ch08) |
| 6 | 최소 차단 게이트 · 짧은 PR | 짧은 PR 수명·빠른 병합, 사람 승인은 판단 필요 시만, 에이전트 검토자 반복 루프 | 2부 6장(ch09) |
| 7 | 백그라운드 태스크 · 자율 루프 | 반복 Codex 태스크(스캔→수정 PR), 점증하는 자율 수준 | 2부 7장(ch10) |
| 8 | 황금 원칙 · doc-gardening | "Golden Principles" + 품질 등급(QUALITY_SCORE) + 정리 PR | 2부 8장(ch11) |

> 8원칙을 **합쳐서** 쓰는 패턴은 3부에서 다룹니다: 진실의 원천 설계(ch12) · 검증 게이트와 모델 다양성(ch13) · 결정론적 산출물(ch14) · 멀티 에이전트 오케스트레이션(ch15). 이 책 레포 자체를 8원칙으로 해부·채점한 사례는 4부(ch16·ch17)에 있습니다.

빠르게 자가 진단하려면 한 가지만 물어보면 됩니다. **"이 규칙은 사람의 주의력에 의존하는가, 프로젝트 저장소가 강제하는가?"** 전자라면 원칙 1, 5, 7 중 무언가가 빠진 것입니다.

## 안티패턴과 함정

- **치트시트를 원문으로 착각하기.** 이 표는 **이 책이 도출한** 8원칙입니다. 원문을 "OpenAI가 번호로 못 박은 목록"처럼 인용하면 출처 오류입니다. 원문은 원칙에 번호를 매기지 않습니다.
- **원칙을 독립 체크리스트로만 보기.** 8원칙은 서로 맞물립니다. 원칙 2(관측성) 없이 원칙 5(기계적 강제)만 깔면, 강제는 되지만 무엇이 깨졌는지 못 봅니다. 진단할 땐 한 원칙이 아니라 이웃 원칙까지 같이 봐야 합니다.
- **데모 기준으로 판단하기.** 위 진단표의 증상은 전부 규모와 시간에서 드러납니다. "지금은 잘 도는데?"는 아직 작아서일 뿐, 원칙이 갖춰졌다는 증거는 아닙니다.
- **강제 없이 표만 붙이기.** 이 치트시트를 `AGENTS.md`에 그대로 붙여도, 린터·CI가 강제하지 않으면 원칙 5를 어기는 셈입니다. 요약은 사람용 지도이고, 강제는 기계의 몫입니다.

## 핵심 정리 / 체크리스트

- [ ] 8원칙은 **원문에서 도출한** 커리큘럼이다(원문은 번호 미부여). 인용은 "도출한 8원칙"으로.
- [ ] 한 줄 명제: **사람이 조종하고, 에이전트가 실행한다.** 나머지 일곱은 이 문장의 전개다.
- [ ] 에이전트가 무너지면, 위 진단표로 **빠진 원칙**부터 찾는다(증상→원칙 역추적).
- [ ] 자가 진단 질문: "이 규칙은 사람의 주의력에 의존하나, 프로젝트 저장소가 강제하나?" → 전자면 원칙 1, 5, 7 점검.
- [ ] 원칙은 **합쳐서** 작동한다. 관측성(2) 없는 강제(5), 강제(5) 없는 자율(7)은 절반만 한다.
- [ ] 요약은 사람용 지도, **강제는 기계**(린터·구조적 테스트·CI)의 몫이다.
